# سلامت‌بان — نسخهٔ ارائه و بررسی محصول

برای **معماری هدف ۱۰۰۰ کاربر فعال**، از [سند معماری و استقرار](deliverables/architecture/SALAMATBAN-1000-USERS-fa.md)، [طراحی دیتابیس و مهاجرت](deliverables/architecture/database-1000-users-fa.md) و [طرح SQL PostgreSQL](deliverables/architecture/postgresql-target-schema.sql) استفاده کنید. این اسناد طراحی نسخهٔ عملیاتی‌اند؛ نسخهٔ نمایشی فعلی یا ظرفیت آزموده‌شدهٔ تولید محسوب نمی‌شوند.

برای معرفی محصول و نظرخواهی از داشبورد `index.html` بسته و [راهنمای کوتاه](deliverables/SHOWCASE-GUIDE-fa.md) شروع کنید. [ساختار فنی و اجرا](deliverables/DEVELOPER-HANDOFF-fa.md) مرجع جزئیات پیاده‌سازی است. نمایش عمومی برای دادهٔ ساختگی است.

- `site/`: برنامه فعال؛ تنها مسیر محصول `/pilot` و API آن فعال است.
- `reference-code/`: آرشیو تاریخی مخزن؛ در ZIP سورس فعال گنجانده نشده و داخل برنامه فعال build نمی‌شود.
- `reference-docs/`: آرشیو تاریخی مخزن، خارج از ZIP سورس فعال؛ تأیید جاری محسوب نمی‌شود.
- `deliverables/`: راهنمای معرفی، تصاویر معماری و وضعیت آمادگی.
- `review-evidence/`: نتایج واقعی آزمون و بررسی وابستگی‌ها؛ اطلاعات ساختگی.
- `scripts/package_complete_delivery.py`: ساخت داشبورد، راهنمای کوتاه و ZIP هماهنگ.
- `deployments/`: بستهٔ نمایشی مستقل از سرور و [راهنمای انتشار در GitHub Pages یا هاست اشتراکی](deployments/README-fa.md).


## هویت و نسخهٔ ارائه سلامت‌بان

نام فعال محصول **سلامت‌بان** است. نام همیار سلامت فقط در منابع تاریخی و نام فایل‌های آرشیو باقی می‌ماند. رابط جدید شامل خانه سلامت، تصویر سلامت، برنامه پیگیری، مدارک، نوبت‌ها، حساب و حریم خصوصی، پشتیبانی و میزهای پزشک، هماهنگی و مدیریت است. اطلاعات و وضعیت‌ها از همان سرویس آزموده‌شده می‌آیند.

- [راهنمای هویت بصری PDF](deliverables/Salamatban-Visual-Identity.pdf) و [دارایی‌های کامل برند](site/public/brand/README-fa.md)
- راهنمای تعاملی هویت: `site/public/brand/index.html`؛ نشان، لوگوتایپ برداری، رنگ‌ها، نمونه رابط و ۹ وزن فونت پیدا
- [معماری و دامنه محصول](deliverables/salamatban-product-architecture-fa.md) و [چک‌لیست تحویل و موارد باز خدمت واقعی](deliverables/salamatban-release-checklist-fa.md)
- [انتشار نسخهٔ نمایشی در Pages یا هاست اشتراکی](deployments/README-fa.md)

سلامت‌بان با هویت مستقل، نشان اختصاصی، پالت آبی و فیروزه‌ای و فونت پیدای ارسالی کاربر ارائه می‌شود. راهنمای رنگ‌ها و قواعد هویت در `site/public/brand/README-fa.md` ثبت شده است. نسخه مرورگری برای نمایش است؛ پیامک، پرداخت و دادهٔ مشترک به راه‌اندازی بک‌اند نیاز دارند.

## اجرای محلی

Node.js 24 توصیه می‌شود. فرمان‌ها در پوشه `site` اجرا شوند:

```sh
npm ci --registry=https://registry.npmjs.org
npm run db:local
PILOT_MODE=demo PILOT_ORIGIN=http://localhost:4173 npm run dev -- --port 4173
```

سپس `http://localhost:4173/pilot` را باز کنید. در بخش «حساب‌های ساختگی» شماره نقش دلخواه را انتخاب کنید؛ کد همان آزمون روی صفحه نشان داده می‌شود. همه داده‌ها باید ساختگی باشند. داده محلی در `site/.wrangler` می‌ماند و داخل بسته تحویل قرار نمی‌گیرد. آزمون‌های خودکار پایگاه موقت جدا می‌سازند و داده نمایش را تغییر نمی‌دهند.

```sh
npm test
npm run lint
npx tsc --noEmit
npm run build
```

فقط مهاجرت‌های `drizzle-pilot/` برای برنامه فعال لازم‌اند. `0000` با Drizzle از `db/pilot-schema.ts` تولید شده؛ `0001` قیود SQL تکمیلی برای هم‌زمانی است. `reference-code/drizzle/` مهاجرت‌های قدیمی است و برای این پایلوت اعمال نشود. برای تغییر بعدی از `npm run db:generate` و مرور SQL استفاده کنید؛ تاریخچه اعمال‌شده بازنویسی نشود.

## راه‌اندازی واقعی

هنوز انجام نشده است. ابتدا تصمیم‌های باز PRD، حساب سرویس‌ها و محیط داده مورد تأیید مالک تهیه شوند. معماری کنونی Cloudflare Workers/D1/R2 است؛ میزبان دیگری نیازمند تطبیق و آزمون دوباره است. شناسه Site داخل آرشیو اولیه در حساب فعلی قابل دسترسی نبود؛ هیچ انتشار از طرف صاحب آن پروژه انجام نشده است.

1. محیط‌های نمایش و واقعی، پایگاه داده و مخزن فایل کاملاً جدا داشته باشند. محیط واقعی هرگز با `PILOT_MODE=demo` اجرا نشود.
2. دامنه HTTPS، اتصال DB و مخزن خصوصی FILES را در میزبان منتخب ایجاد کنید. مهاجرت‌ها ابتدا در staging اعمال و بازیابی پشتیبان تمرین شود.
3. افراد واقعی پزشک، کارشناس و مدیر با شناسه تصادفی و نقش مشخص در `pilot_users` توسط اپراتور مجاز ایجاد شوند. ثبت‌نام عمومی کارکنان وجود ندارد. کلید TOTP هر فرد در secret store قرار گیرد؛ نه داخل SQL، Git یا گفتگو.
4. کلیدها و قیمت در secret store محیط مقصد تنظیم شوند؛ `site/.dev.vars.example` نام متغیرها را نشان می‌دهد. مبلغ ریالی باید صریح و مصوب باشد.
5. واسط اسکن فایل باید قراردادی داشته باشد که بایت‌های فایل را با Bearer token و هدر SHA-256 بپذیرد و فقط برای فایل واقعاً پاک `{ "clean": true, "sha256": "همان مقدار" }` برگرداند. این API اسکنر را پیاده‌سازی نمی‌کند. تنها سرویس مورد تأیید مالک داده انتخاب شود.
6. اتصال درگاه و SMS در مقصد با حساب مالک آزموده شود. تست‌های موجود با پاسخ شبیه‌سازی‌شده، قرارداد verify را بررسی می‌کنند؛ آزمون شبکه واقعی ارائه‌دهنده نیستند.
7. عملیات واقعی بازپرداخت، دریافت/حذف داده، پایش، SLA، اسکن، پشتیبان و آزمون گوشی طبق بک‌لاگ تکمیل شوند. هیچ درخواست پشتیبانی صرفاً با ثبت پاسخ، اجراشده محسوب نمی‌شود.
8. پس از شواهد Go/No-Go، `PILOT_LAUNCH_READY=true` و `CLINICAL_CONTENT_APPROVED=true` تنظیم شود. این دو پرچم جای تأیید و آزمون را نمی‌گیرند. آغاز با ۵ نفر، سپس مجموع ۱۵ و ۵۰ نفر باشد.

## پرداخت و رخداد

مبلغ سروری و Authority ذخیره‌شده مبنای verify است. پاسخ callback، مبلغ مرورگر یا «OK» مجوز فعال‌سازی نیست. سفارش نامشخص قفل می‌ماند. اگر Authority در اثر قطع ارتباط ثبت نشده، اپراتور باید با شناسه سفارش و گزارش درگاه رفع مغایرت کند؛ ایجاد سفارش دوباره یا علامت‌زدن دستی «پرداخت‌شده» مجاز نیست. بازپرداخت فعلی فقط درخواست پشتیبانی است و عملیات مالی خودکار انجام نمی‌دهد.

در رخداد دسترسی اشتباه، داده گمشده یا پرداخت تکراری: پذیرش جدید را متوقف کنید، داده و لاگ شناسایی‌شده را حفظ کنید، مسئول فنی/پزشکی را در جریان بگذارید و پس از رفع علت و تکرار آزمون از سر بگیرید. خاموش‌کردن پرچم launch کل API پایلوت را مسدود می‌کند؛ قبل از استفاده، مسیر پشتیبانی خارج سامانه باید مشخص باشد.

## محدودیت‌های تحویل

تست Android/iPhone واقعی، بار شبکه موبایل، بررسی امنیت مستقل، بکاپ واقعی و اعتبار بالینی هنوز انجام نشده‌اند. هشدارهای باقی‌مانده npm در گزارش نهایی ثبت شده‌اند و با downgrade اجباری پنهان نشده‌اند. نسخه حاضر برای مرور محصول و توسعه است؛ برای شروع پایلوت واقعی فصل آمادگی PRD ملاک است.

## رابط فعلی و بررسی

فرم تک‌سؤال، ذخیرهٔ خودکار، شهر و تاریخ، نقشهٔ اختیاری، پرداخت نمایشی و گردش پزشک و کارشناس اجرا شده‌اند. مدل فعال ۱۴ جدول با مهاجرت‌های `0000` تا `0003` دارد. [دامنهٔ بررسی](deliverables/FLOW-REVIEW-v1.7-fa.md) و [وضعیت UX](deliverables/UX-IMPROVEMENTS-fa.md) را ببینید.

بستهٔ معرفی و برنامهٔ داخل آن نسخهٔ ۲٫۳ هستند. ورود عضو گفت‌وگویی و بدون منوی کناری است؛ شش دلیل مراجعه، هدف کاربر، پنل تدریجی، موشن و بازبینی برنامه در [مسیرهای پرونده](deliverables/JOURNEY-v2.0-fa.md) و [معماری جاری نقش‌ها و فرم‌های گروهی](deliverables/WORKFLOW-ARCHITECTURE-v2.2-fa.md) توضیح داده شده‌اند. حساب‌های نمونه کنار فرم ورود و کد نمایشی قابل کپی است. پیام ذخیره و خطای فیلد در فضای از پیش در نظر گرفته‌شده نمایش داده می‌شوند؛ گرافیک پذیرش و خانهٔ عضو زنده و بدون زمینهٔ سرمه‌ای است. برای پاسخ هشدار، راهنمای کمک فوری با متن متناسب با همان علامت باز می‌شود؛ نتیجهٔ جست‌وجوی بیمارستان بر اساس شهر در خود راهنما دریافت می‌شود. موقعیت دستگاه فقط با انتخاب صریح کاربر درخواست می‌شود. ورود ظاهر تصویری آبی دارد و فهرست شهرها برای انتخاب دقیق‌تر گسترش یافته است. داشبورد شش بخش قابل مرور و تصاویر معماری مستقل دارد. نسخهٔ npm شمارهٔ انتشار محصول نیست.
